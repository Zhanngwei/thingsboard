ThingsBoard 设计思想与架构模式

深入理解平台背后的设计哲学、架构决策和核心模式

1

Actor 并发模型

ThingsBoard 采用自定义的 Actor 模型 来处理海量设备的消息并发。每个设备、每条规则链都是一个独立的 Actor，通过非阻塞消息传递实现高效通信。

为什么选择 Actor 模型？

IoT 平台面临的核心挑战：百万级设备同时上报数据，需要保证同一设备消息的有序性，同时最大化吞吐量。

方案优点缺点
线程池 + 锁简单直观锁竞争严重，难以扩展
Actor 模型无锁、消息隔离、可扩展调试复杂
协程/纤程轻量级Java 生态不成熟(当时)

Actor 层级设计

AppActor (1个，系统级)
├── TenantActor (N个，每租户1个)
│ ├── RuleChainActor (M个，每规则链1个)
│ │ └── RuleNodeActor (K个，每节点1个)
│ └── DeviceActor (P个，每活跃设备1个)
└── TenantActor ...

核心设计决策

1. 每个 Actor 有独立邮箱(Mailbox)：消息先入队，Actor单线程消费，天然保证消息有序

2. 分层调度器(Dispatcher)：不同类型Actor使用不同线程池，避免互相影响

3. 懒加载：DeviceActor 仅在设备有消息时创建，空闲超时后销毁

4. 高优先级队列：生命周期消息(如分区变更)优先于普通消息处理

无锁并发 消息有序性 故障隔离 可水平扩展
2

多租户隔离架构

ThingsBoard 从设计之初就是 原生多租户(Multi-tenant) 架构，所有租户共享同一套基础设施，但数据完全隔离。

隔离机制

1. 数据隔离：每条数据记录都关联 tenant_id，查询时自动过滤

2. 计算隔离：每个租户独立的 TenantActor，规则引擎执行互不干扰

3. 资源隔离：通过 Tenant Profile 配置 API 限流、存储配额、规则节点执行次数等

4. 队列隔离：支持为不同租户配置独立的 Rule Engine 队列

Tenant Profile 资源控制

// 租户配置文件控制资源使用
TenantProfile:
  maxDevices: 1000 // 最大设备数
  maxAssets: 500 // 最大资产数
  maxDashboards: 100 // 最大仪表盘数
  maxRuleChains: 50 // 最大规则链数
  transportTenantMsgRateLimit: "1000:1,20000:60" // 速率限制
  maxREExecutions: 10000000 // 规则引擎月执行次数
共享基础设施降低成本 严格数据隔离 灵活资源配额 SaaS就绪
3

基于队列的解耦架构

ThingsBoard 使用 消息队列(Kafka) 作为所有服务间通信的骨干，实现了完全的生产者-消费者解耦。

队列拓扑

Transport Service ──→ [tb_rule_engine.main] ──→ Rule Engine Service
Transport Service ──→ [tb_core] ──→ Core Service
Core Service ──→ [tb_transport.notifications] ──→ Transport Service
Any Service ──→ [tb_transport.api.requests] ──→ Transport Service
Transport Service ──→ [tb_transport.api.responses] ──→ Requesting Service

设计优势

1. 服务解耦：Transport 不需要知道 Core 的位置，只需写入队列

2. 弹性扩展：任何服务都可以独立扩容，增加消费者即可提升吞吐

3. 消息持久化：Kafka 保证消息不丢失，服务重启后继续消费

4. 背压控制：消费者处理不过来时，消息堆积在队列而非 OOM

5. 分区有序：同一设备的消息进入同一分区，保证有序处理

服务解耦 弹性扩展 消息不丢失 背压控制 有序处理
4

可插拔规则引擎

规则引擎采用 Strategy + Plugin 模式，所有规则节点都是可替换的组件，支持第三方扩展。

插件发现机制

// 1. 通过 @RuleNode 注解标记组件
@RuleNode(type = ComponentType.FILTER, name = "my-filter")
public class MyFilterNode implements TbNode { ... }

// 2. Spring ComponentScan 自动发现
// 3. ComponentDescriptorService 注册到数据库
// 4. UI 从 API 获取可用节点列表

节点生命周期

init(ctx, config) → [等待消息] → onMsg(ctx, msg) → [处理] → tellNext/tellSuccess/tellFailure → destroy()

关注点分离：规则节点只需关注自己的业务逻辑，框架负责消息路由、错误处理、调试追踪。

可扩展 低耦合 热加载 统一生命周期
5

传输层抽象与适配器模式

传输层采用 Adapter Pattern，将不同IoT协议适配为统一的内部消息格式。核心业务逻辑完全不感知具体协议。

统一接口设计

public interface TransportService {
  // 无论 MQTT/CoAP/HTTP，最终都调用这些统一方法
  void process(SessionInfoProto session, PostTelemetryMsg msg);
  void process(SessionInfoProto session, PostAttributeMsg msg);
  void process(SessionInfoProto session, ToServerRpcRequestMsg msg);
}

协议适配流程

MQTT PUBLISH → MqttTransportHandler.channelRead() → 解析topic和payload
  → adaptorService.convertToPostTelemetry(mqttMsg)
  → transportService.process(session, PostTelemetryMsg)
  → 编码为Protobuf → 发送到Kafka

这意味着添加新协议只需要实现协议解析和适配层，核心处理逻辑完全复用。

协议无关 易于扩展新协议 核心逻辑复用
6

基于分区的水平扩展

ThingsBoard 通过 一致性分区(Consistent Partitioning) 实现集群水平扩展。每个实体(设备)被映射到固定的分区，分区分配给具体的服务节点。

分区算法

// 计算实体所属分区
partition = hash(entityId) % totalPartitions

// 分区分配给节点
Node A: partitions [0, 1, 2, 3]
Node B: partitions [4, 5, 6, 7]
Node C: partitions [8, 9, 10, 11]

扩展场景

1. 新节点加入：Zookeeper 感知，触发分区重新分配，部分分区迁移到新节点

2. 节点退出：该节点的分区重新分配给存活节点

3. 消息路由：Transport 计算目标分区，写入对应 Kafka Partition

4. Actor重建：新负责节点重建该分区内的 Actor 状态

保证

• 同一设备的消息始终由同一节点处理（有序性）
• 扩容时仅部分设备受影响（最小化迁移）
• 无需外部协调即可确定消息路由（高效）

线性扩展 消息有序 最小化迁移 无单点
