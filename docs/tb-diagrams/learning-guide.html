💡 核心概念速览

🏢 多租户架构

ThingsBoard 原生支持多租户隔离：

  • SysAdmin → 管理所有租户
  • Tenant → 独立业务单元
  • Customer → 租户的子客户
  • 数据完全隔离，互不可见

📡 设备连接

灵活的设备接入方式：

  • MQTT - 最主流的IoT协议
  • CoAP - 低功耗受限设备
  • HTTP - 简单场景
  • 网关设备 - 代理子设备

🔗 规则引擎

可视化的消息处理流水线：

  • Rule Chain - 处理流水线
  • Rule Node - 处理单元
  • 支持 JS/TBEL 脚本
  • 可扩展自定义节点

📊 数据模型

三种核心数据类型：

  • Telemetry - 时序遥测数据
  • Attributes - 键值属性(3类)
  • Events - 系统事件日志

🚨 告警系统

完整的告警生命周期：

  • 条件触发(阈值/不活跃等)
  • 5级严重程度
  • 告警传播(设备→资产)
  • 通知渠道(邮件/短信/Slack)

🎭 Actor 模型

高并发消息处理框架：

  • 每设备独立Actor
  • 非阻塞消息传递
  • 层级结构自动路由
  • 故障隔离和恢复

❓ 常见问题

ThingsBoard 单体和微服务有什么区别？
单体模式(Monolith)将所有功能打包在一个Java进程中，适合开发测试和小规模部署。微服务模式将Transport、Core、Rule Engine拆分为独立进程，通过Kafka通信，支持独立扩展，适合生产环境。代码是同一套，区别在于部署方式和Spring Profile。
为什么使用自定义 Actor 模型而不是 Akka？
ThingsBoard 早期使用 Akka，后来切换为自定义轻量级 Actor 框架。原因：1) 减少依赖复杂度；2) 针对IoT场景优化（海量设备Actor）；3) 更容易控制线程模型和资源使用；4) 避免 Akka 许可证问题。
规则引擎消息(TbMsg)和Kafka消息是什么关系？
TbMsg 是规则引擎内部的消息对象，包含消息类型、数据、元数据和来源实体。它通过 Protobuf 序列化后封装为 Kafka 消息进行传输。从Kafka消费后反序列化回 TbMsg，再在 Actor 系统中流转。
设备如何保证消息有序性？
通过 entityId 的 hash 将同一设备的消息路由到同一个 Kafka 分区，同一分区内消息严格有序。同一个 Core 节点消费该分区，保证同一设备的消息串行处理。
如何自定义开发规则节点？
1) 创建类实现 TbNode 接口；2) 添加 @RuleNode 注解（指定类型、名称、配置类）；3) 实现 init/onMsg/destroy 方法；4) 创建对应的前端配置组件。打包后平台自动发现并注册。
💡 学习建议： 建议先在本地启动ThingsBoard，通过UI创建设备并发送数据，实际体验完整流程后再深入源码。理论结合实践效果最佳！
