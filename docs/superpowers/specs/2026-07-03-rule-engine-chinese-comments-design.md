# Rule Engine 中文注释设计

## 背景

目标是在 ThingsBoard `rule-engine` 模块内增加高质量中文注释，帮助读者理解 Rule Engine 的架构职责、节点生命周期、消息处理流程、外部系统协作、数据库/缓存/事务/MQTT/Actor/Rule Engine 相关行为。

本工作只增加注释，不修改业务逻辑、变量名、方法签名、代码格式和原有代码结构。

## 范围

覆盖 `rule-engine` 下全部 Java 文件：

- `rule-engine/rule-engine-api/src/main/java`
- `rule-engine/rule-engine-api/src/test/java`
- `rule-engine/rule-engine-components/src/main/java`
- `rule-engine/rule-engine-components/src/test/java`

不覆盖非 Java 文件，不覆盖仓库中其它模块。

## 分批策略

采用按架构层分批的方式推进：

1. `rule-engine-api`
   - 先注释 Rule Engine 对外抽象、节点接口、上下文、工具类和测试。
   - 这一批用于建立统一术语，例如 `TbNode`、`TbContext`、`TbMsg`、回调、关系类型、节点配置。
2. `rule-engine-components` 基础设施
   - 注释 `util`、抽象基类、通用回调包装、实体加载器等共享组件。
   - 重点说明这些类如何被多个节点复用，以及为什么抽象成公共能力。
3. 核心规则节点包
   - 按 `metadata`、`filter`、`transform`、`action`、`telemetry`、`profile`、`flow`、`deduplication` 等包推进。
   - 重点说明节点在规则链中的输入、输出、关系路由和错误处理。
4. 外部集成节点包
   - 按 `mqtt`、`kafka`、`rabbitmq`、`rest`、`aws`、`gcp`、`mail`、`sms`、`notification` 等包推进。
   - 重点说明与外部协议、外部服务、异步调用和连接生命周期的关系。
5. 测试代码
   - 在对应生产代码批次后补充测试类注释。
   - 重点说明测试场景、被验证流程、Mock 数据来源和断言目的。

## 注释规范

### 类注释

每个类、接口、枚举、record 补充中文 Javadoc 或块注释，说明：

- 这个类型存在的目的。
- 在 ThingsBoard 中属于哪个模块或子流程。
- 与哪些模块或服务协作。
- 生命周期。
- 为什么需要该类型，而不是直接在调用方实现。
- 如涉及设计模式，标注 Factory、Strategy、Template、Observer、Actor、Builder、Decorator、Command 等模式。

### 字段注释

每个字段补充中文注释，说明：

- 字段保存的数据。
- 数据来源。
- 生命周期。
- 为什么设计成字段，而不是局部变量、常量、配置或方法参数。

### 方法注释

每个方法补充中文 Javadoc 或块注释，说明：

- 方法职责。
- 输入参数意义。
- 返回值意义。
- 调用时机。
- 调用方。
- 被哪些 Rule Engine 流程使用。
- 是否线程安全。
- 是否涉及事务。
- 是否涉及缓存。
- 是否涉及 MQTT。
- 是否涉及 Actor 通信。
- 是否涉及数据库。
- 是否涉及 Rule Engine。

### 行内注释

复杂分支、异步回调、异常处理、消息路由、状态迁移、缓存命中/失效、数据库访问、外部协议调用处增加行内中文注释。

行内注释只解释设计原因和非显而易见的行为，不重复代码字面含义。

## 文件级总结

每个 Java 文件末尾增加“本类总结”注释，包含：

- 核心职责。
- 核心流程。
- 关键依赖。
- 学习重点。

如果一个文件内有多个顶层类型，总结以主类型为核心，同时点明辅助类型的作用。

## 禁止事项

- 不修改原有代码。
- 不修改变量名。
- 不修改方法名、方法参数、返回类型或可见性。
- 不修改类继承结构、注解、导入、包名。
- 不调整代码格式。
- 不删除或替换已有英文注释，只在必要处追加中文解释。
- 不通过格式化工具重排文件。

## 验证方式

每批完成后执行：

1. `git diff --check`
   - 检查空白错误。
2. 针对批次相关 Maven 模块执行测试或至少编译：
   - `mvn -pl rule-engine/rule-engine-api test`
   - `mvn -pl rule-engine/rule-engine-components test`
3. 人工抽查 diff，确认所有变更均为注释。

如果完整测试耗时过长，至少执行对应模块的编译，并在结果中明确说明未运行完整测试。

## 风险与控制

- 风险：一次性修改 305 个 Java 文件会造成巨大 diff，难以审查。
  - 控制：按架构层分批提交或分批交付。
- 风险：注释过度膨胀导致源码阅读噪音增加。
  - 控制：类/字段/方法注释覆盖要求，行内注释只解释复杂或架构性原因。
- 风险：对线程安全、事务、缓存、Actor、MQTT、数据库等判断不准确。
  - 控制：先从 API 和基类理解调用链，再注释具体节点；无法从当前类直接确认时，用“本类本身不直接涉及”而不是过度推断。
- 风险：自动格式化改变代码。
  - 控制：不运行格式化工具，不做机械重排。

## 验收标准

- `rule-engine` 下全部 Java 文件均新增中文注释。
- 原业务代码保持不变。
- 每个类、字段、方法的注释覆盖用户指定维度。
- 复杂代码具备必要行内解释。
- 每个文件包含“本类总结”。
- 每批验证命令完成，并报告结果。
