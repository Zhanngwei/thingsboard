第一部分：MySQL 与 PostgreSQL 全面对比

1. 设计哲学：产品边界不同

MySQL 在工程心智上通常以 InnoDB 为中心：SQL 层解析、优化、执行，存储引擎层完成事务、索引、Buffer Pool、redo/undo、锁。这个边界非常清晰，也形成了 MySQL 工程师熟悉的“server layer + engine layer”。

PostgreSQL 更像一个数据库操作系统：进程管理、共享内存、WAL、事务状态、锁管理、buffer manager、存储访问方法、扩展机制、后台 worker、复制协议都在同一套内核框架内协同。它不是把复杂能力藏在某个可替换引擎里，而是把能力做成可扩展的内核接口：access method、operator class、extension、foreign data wrapper、logical decoding、background worker、custom scan 等。

MySQL 的优势直觉

路径短、生态广、主从部署成熟、InnoDB 行为稳定、在线 OLTP 易上手。简单主键查询、短事务、互联网 CRUD 场景很顺。

PostgreSQL 的优势直觉

SQL 能力更完整，复杂查询、窗口函数、CTE、递归、JSONB、数组、GIS、扩展、并行查询和统计驱动优化器更强，适合把更多业务语义推到数据库内。

2. 存储引擎对比

3. WAL 与 Binlog 对比

MySQL 工程师容易把 PostgreSQL WAL 类比成 MySQL redo log 或 binlog，但它更接近“redo + 物理复制 + crash recovery 的统一日志”。MySQL redo 是 InnoDB 内部物理日志，binlog 是 server 层逻辑日志；PostgreSQL WAL 是内核统一的预写日志，提交、checkpoint、物理流复制、崩溃恢复、逻辑解码都围绕 LSN 展开。

4. MVCC 实现差异

InnoDB 的记录有隐藏列和 undo 链，读旧版本时沿 undo 回溯。PostgreSQL 的 heap tuple 头部包含 xmin、xmax、ctid 等元数据，更新是“插入新版本 + 标记旧版本 xmax”，版本链在 heap 中通过 ctid 连接。事务提交状态不写在 tuple 自身的完整事务对象里，而是通过 pg_xact（旧称 CLOG）、hint bit、snapshot 的 xmin/xmax/xip 共同判断。

5. 锁机制差异

MySQL/InnoDB 的锁心智以 record lock、gap lock、next-key lock、insert intention 为主，Repeatable Read 下靠 next-key lock 防幻读。PostgreSQL 的常规 MVCC 读不加行锁，行锁通过 tuple header 的 xmax、MultiXact 和锁表协同表达；表级锁模式多但多数 DML 之间兼容。PostgreSQL Serializable 使用 SSI（Serializable Snapshot Isolation）跟踪读写依赖，而不是用大范围 gap lock 作为主路径。

6. 执行器架构差异

MySQL 优化器相对保守，执行器长期以 nested-loop 为基础，复杂计划能力在新版本持续增强。PostgreSQL 的执行器是 volcano iterator 模型，每个 plan node 暴露类似 ExecProcNode 的接口，上层节点不断向下拉取 tuple。Hash Join、Merge Join、Nested Loop、Bitmap Heap Scan、Append、Gather、Materialize、Aggregate 等节点组合能力强。

7. Buffer 管理差异

InnoDB Buffer Pool 直接承载绝大多数缓存策略，包括 LRU、change buffer、自适应 hash 等。PostgreSQL shared buffers 是数据库内共享页缓存，但 PostgreSQL 仍强依赖操作系统 page cache；它用 clock sweep 近似 LRU，后台 writer 平滑刷脏页，checkpoint 负责恢复边界。高写入场景不是只看 shared buffers 命中率，还要看 checkpoint 写放大、WAL fsync、脏页比例和 OS cache。

8. 索引体系差异

索引类型PostgreSQL 典型用途MySQL 对照
B-tree等值、范围、排序、唯一约束，最常用。类似 InnoDB B+Tree，但二级索引指向 heap TID，不包含主键聚簇行。
Hash等值查询，现代版本 WAL 安全，但仍不如 B-tree 通用。MySQL Hash 多见于 Memory 或自适应 hash 内部。
GINJSONB、数组、全文检索倒排索引。MySQL JSON 索引通常靠 generated column 或 multi-valued index。
GiST / SP-GiST几何、范围、KNN、PostGIS。MySQL GIS 能力相对有限。
BRIN大表顺序相关数据，例如时间序列。类似“块级 min/max 摘要”，MySQL 无直接等价。
Partial / Expression只索引满足条件的行，或索引表达式。MySQL 可用函数索引但 partial index 能力弱。

9. JSONB vs MySQL JSON

MySQL JSON 是二进制 JSON 文档，路径提取和 generated column 索引常见。PostgreSQL jsonb 是解析后的二进制结构，支持包含、存在、路径、GIN 索引、表达式索引。ThingsBoard 当前 schema 中遥测和属性列使用 json 而不是 jsonb，因为它的典型访问模式是按 entity_id + key + ts 找值，JSON 内容更多是值载荷而非频繁内部检索对象。

10. 分区表对比

MySQL 分区常被视为超大表管理手段，但优化器和全局索引限制会影响使用体验。PostgreSQL declarative partitioning 的路由、裁剪、分区 pruning 与 planner/executor 集成较深；TimescaleDB 在此基础上提供 hypertable，把“按时间分 chunk”的管理自动化。

11. 并发机制对比

MySQL 一个连接通常对应一个线程，线程缓存和连接池可缓解开销。PostgreSQL 一个连接通常对应一个 backend 进程，进程有私有内存、事务状态、临时上下文，连接数过高会造成上下文切换、内存和锁管理开销。生产中 PgBouncer / HikariCP 参数是数据库架构的一部分。

12. 崩溃恢复对比

InnoDB 通过 checkpoint LSN、redo log、undo 回滚未提交事务，binlog 通过两阶段提交保证 server 层与 InnoDB 的一致性。PostgreSQL 从 checkpoint record 开始扫描 WAL，redo 到一致点；未提交事务的 tuple 因提交状态不可见，后续 Vacuum 清理，不需要像 InnoDB 那样用 undo 物理回滚每个旧版本。

13. 查询优化器差异

PostgreSQL planner 高度依赖统计信息：pg_statistic 中的 MCV、histogram、null fraction、correlation、ndistinct 会影响成本估算。它支持 join order 搜索、GEQO、并行计划、partition pruning、extended statistics。迁移后慢查询排查第一步不是“强制索引”，而是确认统计信息、选择率、相关性、work_mem 和 join 算法。

14. PostgreSQL 的优势与缺点

优势：SQL 完整性、复杂查询、扩展生态、JSONB/GIS/全文、事务语义严谨、逻辑复制、索引类型丰富、TimescaleDB 这类扩展可以深度嵌入优化器。
代价：连接模型更重；更新会产生 heap 膨胀；Vacuum/Freeze 需要运维；写入高峰受 WAL/checkpoint 影响明显；参数调优需要理解内核机制。

15. PostgreSQL 常见误区

  • 误区一：把 shared_buffers 当成 InnoDB Buffer Pool，直接给 70% 内存。PostgreSQL 还依赖 OS cache，过大可能增加 checkpoint 压力。
  • 误区二：认为没有 undo 就不需要清理旧版本。PostgreSQL 旧版本在 heap 中，Vacuum 是必需品。
  • 误区三：以为 VACUUM FULL 是常规维护。它会重写表并需要强锁，生产应优先 autovacuum、普通 vacuum、合理 fillfactor 和分区/drop chunk。
  • 误区四：慢查询优先找“用哪个索引”。PostgreSQL 要先看 EXPLAIN (ANALYZE, BUFFERS) 中估算行数和真实行数偏差。
  • 误区五：TimescaleDB 等于另一个数据库。它是 PostgreSQL 扩展，底层仍受 WAL、Vacuum、checkpoint、planner 和连接模型影响。

3. backend process 模型

每个 backend 有私有内存上下文、事务状态、Portal、PreparedStatement、临时文件、work_mem 消耗。一个 SQL 中多个 Sort/Hash 节点都可能各自使用 work_mem，并发连接数乘以复杂计划节点数才是内存风险。

MySQL 对照：MySQL 线程栈、join_buffer、sort_buffer、read_buffer 等按线程消耗；PostgreSQL 的进程私有内存更强调 memory context 生命周期，例如 TopMemoryContext、CacheMemoryContext、PortalContext、ExecutorState。

6. CLOG / XID 原理

CLOG 现在目录名为 pg_xact，保存事务 ID 的提交状态：in progress、committed、aborted、sub-committed。tuple 头部只放 xmin/xmax，可见性判断会查询事务状态。hint bit 是把已知提交/回滚状态缓存到 tuple header，减少未来查 pg_xact 的成本，但第一次设置 hint bit 会使页面变脏。

7. Checkpoint 原理

Checkpoint 写出一个恢复边界：保证该 checkpoint 之前的脏页最终刷到数据文件，并在 WAL 中写 checkpoint record。崩溃恢复从最近 checkpoint 开始重放 WAL。过于频繁的 checkpoint 会造成写放大；过少会让恢复时间和 WAL 占用增加。

8. bgwriter 原理

bgwriter 不建立一致性边界，它只提前把脏页写回，减少用户 backend 在找 victim buffer 时被迫刷脏页。MySQL 里你可能关注 page cleaner 和 flushing；PostgreSQL 则要区分 bgwriter 平滑写、checkpointer 边界写、backend write 三种来源。

9. autovacuum 原理

autovacuum launcher 周期性扫描数据库，根据表的 dead tuples、insert/update/delete 计数、freeze 年龄决定启动 worker。worker 对表执行 vacuum/analyze/freeze。它不是“可开可关的优化器”，而是 PostgreSQL MVCC 的清道夫和防事务 ID 回卷机制。

10. stats collector 原理

新版本 PostgreSQL 使用共享内存统计架构替代旧式独立 collector 文件路径。你在 pg_stat_activity、pg_stat_statements、pg_stat_bgwriter、pg_stat_wal、pg_stat_all_tables 看到的是诊断入口。慢查询定位时，统计信息是 planner 的输入，也是 DBA 的观测面。

11. logical replication 原理

逻辑复制通过 logical decoding 把 WAL 解释成表级变更流，依赖 replication slot 保留 WAL。发布端 publication 选择表和动作，订阅端 subscription 接收并 apply。和 MySQL row binlog 相似，但 PostgreSQL 的逻辑复制来自 WAL 解码，不是另一个 binlog 文件。

1. WAL 写入流程

PostgreSQL 的 WAL 是物理重做日志。任何会修改持久化数据页的操作，都先生成 WAL record，拿到 LSN，再修改 buffer 页面并设置 page LSN。提交时写 commit record，按 synchronous_commit 策略决定是否等待 WAL flush。

2. Group Commit

多个 backend 同时提交时，只有一部分进程真正执行 fsync，其他进程等待同一个或更靠后的 LSN 被刷盘。这个机制类似 MySQL group commit，但 PostgreSQL 的提交等待围绕 WAL flush LSN 展开。高并发 ThingsBoard 遥测写入场景中，批量队列能把应用层 batch 和数据库 WAL group commit 叠加起来。

3. fsync 与持久化

fsync=on 是生产底线。关闭 fsync 不是“快一点但可能丢最后几秒”，而是可能在 OS/硬件崩溃时损坏数据一致性。synchronous_commit=off 的风险相对可控：数据库不会坏，但最近已返回成功的事务可能丢失。

4. Checkpoint

Checkpoint 把恢复起点向前推进。checkpoint_timeout 控制时间周期，max_wal_size 控制 WAL 空间触发，checkpoint_completion_target 控制写出平滑度。大量写入时如果日志频繁出现 checkpoint too frequent，应增大 max_wal_size。

5. Crash Recovery

崩溃恢复不扫描所有 heap 表，而是读取 checkpoint redo pointer 之后的 WAL。WAL record 是幂等重放：如果页面 LSN 已经大于等于 record LSN，说明该修改已在数据页，无需重复。未提交事务产生的 tuple 在可见性判断时不可见，后续 Vacuum 清理。

10. Hint Bit

第一次读取某个 tuple 时，如果发现 xmin 已提交，backend 可能设置 HEAP_XMIN_COMMITTED hint bit。这个小优化会让只读查询也可能弄脏页面，因此在主备、校验和、WAL hint 配置下，第一次大范围扫描可能产生额外写 IO。

11. VACUUM

普通 Vacuum 做三件事：找到不再被任何 snapshot 需要的 dead tuple；清理索引中的 dead TID；把 heap 空间登记到 FSM，把全可见页面标记到 VM。它通常不把表文件还给 OS，除非末尾页全部空闲可以 truncate。VACUUM FULL 会重写表，能释放空间但需要强锁。

12. Autovacuum

默认触发公式大致是：autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * reltuples。大表使用默认 20% scale factor 往往太晚，IoT 时序表如果有 DELETE TTL，会积累大量 dead tuple；更推荐 TimescaleDB retention/drop chunk 或 PostgreSQL 分区 drop，而不是逐行 DELETE。

13. Freeze

事务 ID 是 32 位，会回卷。Freeze 把非常老的 tuple 标记成冻结事务，使其对所有未来事务可见。若数据库接近 wraparound，PostgreSQL 会强制 aggressive vacuum，严重时阻止写入。监控 age(datfrozenxid) 和表级 age(relfrozenxid) 是生产必做。

15. Dead Tuple

Dead tuple 是 PostgreSQL heap MVCC 的自然产物。它可能来自 UPDATE、DELETE、失败插入、ON CONFLICT 更新。对 ThingsBoard 来说，ts_kv 是追加为主，但 ON CONFLICT(entity_id,key,ts) DO UPDATE 遇到重复时仍会产生旧版本；ts_kv_latest 最新值表高频 upsert，更容易产生 dead tuple 和索引膨胀。

16. Visibility Map

VM 标记某个 heap page 是否 all-visible 或 all-frozen。Index-only scan 是否真的不回表，很大程度取决于 VM。高更新表 VM 位会频繁被清除，因此即便索引覆盖列，仍可能大量 heap fetch。

17. Free Space Map

FSM 记录每个页面大致剩余空间，插入/更新时用来寻找可放入 tuple 的页面。Vacuum 清理后会更新 FSM。表膨胀不只是磁盘问题，也会拉低 cache density、增加 seq scan 和 index scan 的 heap 访问成本。

2. 行锁

行锁不是集中存在内存锁表里的每一行对象，而是写入 tuple header 的 xmax，必要时使用 MultiXact 表达多个 locker。等待者通常等待持有者的 transactionid。常见模式：FOR UPDATE、FOR NO KEY UPDATE、FOR SHARE、FOR KEY SHARE。

3. 表锁

INSERT/UPDATE/DELETE 通常拿 RowExclusiveLock；SELECT 拿 AccessShareLock；DDL 如 ALTER TABLE 可能拿 AccessExclusiveLock，会阻塞普通读写。生产变更要重点检查 DDL 锁级别和长事务。

4. Advisory Lock

Advisory lock 是应用定义的 64-bit 或两个 32-bit key 锁，可事务级或会话级。它不保护具体表行，适合分布式任务互斥、租户级串行化等。误用会造成连接泄露后锁长期保留，特别是 session-level advisory lock。

5. MVCC 与锁的关系

普通 SELECT 使用 snapshot，不阻塞写；写写冲突才等待。同一行 UPDATE 时，后来的事务需要等待前一个事务结束，再判断是否可更新或报序列化错误。和 InnoDB RR 下 next-key lock 防幻读不同，PostgreSQL Read Committed/Repeatable Read 更多依赖 MVCC snapshot，Serializable 再用 SSI 检测危险结构。

8. Snapshot Isolation

PostgreSQL 的 Repeatable Read 实际提供 snapshot isolation：事务第一次查询时建立 snapshot，后续读取同一 snapshot，不看到其他事务提交的新行。因此普通幻读不会出现。但 write skew 这类异常仍可能发生，需要 Serializable 或显式锁。

10. PostgreSQL 与 MySQL RR 的区别

MySQL InnoDB RR 的锁定读和更新路径可能产生 gap/next-key lock，阻塞插入以防幻读。PostgreSQL RR 不使用 gap lock 作为主机制；读 snapshot 固定，写冲突通过行版本和序列化错误处理。迁移时，依赖 MySQL gap lock 做业务互斥的逻辑需要重新设计。

11. PostgreSQL 幻读机制

Read Committed 下每条语句 snapshot 不同，可以看到新插入行。Repeatable Read 下同一事务 snapshot 固定，看不到新行。Serializable 下如果业务读谓词和其他事务写入形成不可串行化结构，会通过 SSI 报错。

12. 悲观锁

使用 SELECT ... FOR UPDATE 或 FOR NO KEY UPDATE。生产建议加 NOWAIT 或 SKIP LOCKED 用于任务队列，避免无限等待。JDBC 事务必须短，不能在锁内做远程调用。

13. 乐观并发

PostgreSQL 支持常规版本列乐观锁。ThingsBoard 多张表有 version BIGINT；ts_kv_latest 使用 ts_kv_latest_version_seq 在 upsert 后返回版本，配合缓存失效。对遥测历史 ts_kv，主键 (entity_id,key,ts) 加 ON CONFLICT DO UPDATE 提供幂等写。

7. Seq Scan

Seq Scan 不是一定坏。大范围扫描、低选择率、表很小、并行扫描、缓存命中高时，顺序扫描可能比索引随机访问更便宜。PostgreSQL 成本模型中 seq_page_cost、random_page_cost、表相关性会影响选择。

8. Index Scan

Index Scan 从索引找到 TID，再访问 heap。对高度选择性查询有效。因为 PostgreSQL 表不是主键聚簇，索引扫描可能产生大量随机 heap fetch；如果数据按时间写入而按时间范围查，BRIN 或 Timescale chunk pruning 可能更合适。

9. Bitmap Scan

Bitmap Index Scan 先构造 TID 位图，Bitmap Heap Scan 再按 heap block 顺序回表，适合中等选择率或多个索引 AND/OR。若 work_mem 不足，位图会 lossy，导致更多 recheck。

17. PostgreSQL 慢查询定位

  1. 先启用 pg_stat_statements，按 total_time、mean_time、calls、shared_blks_read 排序。

  3. 看是否读了过多 heap block、是否 temp spill、是否 nested loop 放大、是否等待锁或 IO。

5. 时序查询优化

TimescaleDB 优化的关键不是“把所有查询变快”，而是让时间谓词、chunk 元数据、局部索引、压缩段、聚合策略配合。ThingsBoard 的聚合查询使用 time_bucket(:timeBucket, tskv.ts, :startTs)，按时间桶聚合 AVG/MAX/MIN/SUM/COUNT。

6. 压缩机制

TimescaleDB 压缩把较老 chunk 转成列式/压缩布局，适合历史数据少更新、多扫描聚合的场景。压缩后按 segment/order 组织能减少 IO。注意：压缩 chunk 上的 UPDATE/DELETE 成本更高，最新写入 chunk 不应压缩。

8. Retention Policy

时序数据 TTL 最好通过 drop chunk 实现，而不是逐行 DELETE。逐行 DELETE 会产生海量 dead tuple，需要 Vacuum；drop chunk 是删除整张子表，速度快、WAL 少得多、不会制造同等规模的 dead tuple。当前 ThingsBoard schema-timescale 中仍提供 cleanup_timeseries_by_ttl 过程逐行删除符合租户/客户 TTL 的 ts_kv，这意味着大规模场景要格外关注 Vacuum 和 TTL 策略。

12. TimescaleDB 与 Elasticsearch 对比

Elasticsearch 适合全文检索、日志搜索和倒排索引聚合，但事务、一致性、关系 join 和精确更新不是强项。TimescaleDB 适合结构化时序、SQL 聚合、与实体表 join、强一致写入。IoT 遥测如果主要是数值时间范围聚合，TimescaleDB 更直接；如果主要是日志检索和模糊搜索，ES 更合适。

13. IoT 时序模型设计

ThingsBoard 使用窄表模型：entity_id 表示设备/资产等实体，key 是遥测键的整数 ID，ts 是毫秒时间戳，值列按类型拆成 bool_v/str_v/long_v/dbl_v/json_v。优点是 schema 稳定、高基数 key 不改表；代价是一个设备一次上报多个 key 会变多行，聚合需要按 key 过滤。

14. 高基数问题

IoT 高基数主要来自设备数、租户数、遥测 key 数。PostgreSQL/TimescaleDB 不像某些标签型 TSDB 那样把所有 tag 组合建倒排索引，但高基数仍会影响索引大小、chunk 数、统计信息和 cache locality。ThingsBoard 用 key_dictionary 把字符串 key 映射成 int，是典型降宽优化。

15. 写入热点问题

按时间分 chunk 会让所有最新数据进入当前 chunk，形成活跃 chunk 热点。PostgreSQL 单表/单 chunk 写入依赖 WAL 顺序写、索引更新和 buffer 命中。优化方向：批量写、减少二级索引、合理 chunk interval、分散 entity_id、必要时多节点/分库。

17. TTL 清理

当前 schema 中 cleanup_timeseries_by_ttl 会按 tenant/customer 的 TTL 属性查 attribute_kv，再删除 ts_kv 中早于阈值的数据。工程风险是 DELETE 会生成 dead tuple。大规模场景应优先把 TTL 与 chunk 边界对齐，使用 retention/drop chunk；若必须按租户/客户差异 TTL 删除，则要降低 autovacuum 阈值并控制批量大小。

18. Chunk Index 原理

Hypertable 上的索引会传播到 chunk，成为每个 chunk 的本地索引。ts_kv 主键 (entity_id,key,ts) 对单设备单 key 时间范围查询友好；如果大量查询按时间扫描多个实体，可能需要额外以 ts 开头或 BRIN 的索引，但写入成本会增加。

20. 超大规模设备写入优化

  • 应用层批量：ThingsBoard 已用 TbSqlBlockingQueueWrapper 聚合写入，关注 batch size、max delay、batch threads。
  • 数据库层批量：JDBC batch + WAL group commit，避免每个点独立事务。
  • 索引最小化：历史表只保留真正服务查询的索引，最新表单独承载 dashboard 当前值。
  • chunk interval：让活跃 chunk 不过大，历史 chunk 数不过多；常用目标是活跃 chunk 能被 cache 和 autovacuum 管住。
  • TTL 策略：优先 drop chunk；逐行 DELETE 必须配合 aggressive autovacuum。
  • 连接控制：多 ThingsBoard 节点总 Hikari 连接不能压垮 PostgreSQL backend。

第八部分：ThingsBoard + PostgreSQL + TimescaleDB

1. ThingsBoard 为什么使用 PostgreSQL

ThingsBoard 不只是时序写入系统，它还有租户、客户、设备、资产、仪表盘、规则链、告警、权限、审计、事件、实体关系等强关系模型。PostgreSQL 能同时处理元数据事务、复杂实体查询、JSON 字段、事件分区和遥测表；TimescaleDB 则在保持 SQL/JDBC/事务生态的同时增强时序分片和聚合。

2. ThingsBoard 时序表结构

当前仓库的关键 SQL 文件：

  • dao/src/main/resources/sql/schema-timescale.sql：TimescaleDB 扩展、ts_kv、key_dictionary、ts_kv_latest、TTL 清理过程。
  • application/src/main/java/org/thingsboard/server/service/install/TimescaleTsDatabaseSchemaService.java：安装时执行 create_hypertable('ts_kv','ts')。
  • dao/src/main/java/org/thingsboard/server/dao/sqlts/timescale/TimescaleTimeseriesDao.java：Timescale 历史遥测 DAO。
  • dao/src/main/java/org/thingsboard/server/dao/sqlts/insert/timescale/TimescaleInsertTsRepository.java：批量 INSERT ... ON CONFLICT DO UPDATE。

3. entity 与 telemetry 的关系

entity_id 是遥测模型的核心外键语义，但 ts_kv 不是对每种实体建外键约束，而是统一承载 device、asset、entity view 等实体遥测。这避免高写入时外键检查成本，也让遥测层保持窄表通用模型。业务层通过 entity type 和 DAO/service 保证语义。

4. attribute 存储结构

attribute_kv(entity_id, attribute_type, attribute_key) 存属性，值列同样按类型拆分，attribute_key 指向 key_dictionary.key_id。这和遥测表同构，方便统一 KV 模型。TTL 配置也通过属性表读取：schema 中会查 key 为 TTL 的 attribute。

5. event 存储

ThingsBoard 把 debug/stats/lifecycle/error 等事件拆成多张按时间分区表，例如 rule_node_debug_event、rule_chain_debug_event、stats_event、lc_event、error_event，并在 PostgreSQL addon index 中按 (tenant_id, entity_id, ts DESC) 建索引。这是事件查询按租户/实体/时间倒序读取的典型设计。

8. PostgreSQL 在 ThingsBoard 中的事务模型

ThingsBoard DAO 层大量使用 Spring/JPA/JdbcTemplate。遥测历史写入通过批量队列异步提交，不是每个设备消息都直接在业务线程同步写库。最新遥测 upsert 使用版本序列返回版本，支持缓存一致性。元数据表则更典型地走 JPA repository 和事务边界。

9. TimescaleDB 在 ThingsBoard 中如何工作

启用 database.ts.type=timescale 后，@TimescaleDBTsDao 条件装配 Timescale DAO。安装 profile 下创建 Timescale 扩展和 hypertable。历史遥测 ts_kv 走 hypertable；最新遥测 ts_kv_latest 仍是普通表模型，用于快速读取当前值。

10. ThingsBoard 时序查询优化

  • 所有历史查询必须带 entity_id、key、明确 ts 范围。
  • 聚合查询优先用 time_bucket，避免应用层拉全量点再聚合。
  • 仪表盘最新值走 ts_kv_latest，不要从 ts_kv 反查最新点。
  • 跨大量设备的同 key 查询要警惕主键顺序 (entity_id,key,ts) 不适合按 key/time 全局扫描。
  • 大窗口报表考虑 continuous aggregate 或离线汇总表。

11. 高并发设备接入场景

瓶颈链路通常是：Transport 收包、队列积压、Rule Engine 处理、SQL batch queue、JDBC pool、PostgreSQL WAL fsync、当前 chunk 索引写入、ts_kv_latest upsert 行锁/膨胀。定位时不要只看数据库 CPU，要同时看 ThingsBoard 队列统计和 PostgreSQL wait events。

12. ThingsBoard PostgreSQL 调优

  • 连接池：spring.datasource.hikari.maximumPoolSize 默认 16，多节点总和要受控。
  • WAL：提高 max_wal_size，使用快 SSD/NVMe，监控 pg_stat_wal。
  • Vacuum：对 ts_kv_latest、attribute_kv 设置更激进 autovacuum；避免长事务阻塞 vacuum。
  • 分区/Timescale：历史 TTL 优先 drop partition/chunk，减少 DELETE。
  • 统计：高变更表降低 analyze scale factor，慢查询先看估算偏差。

13. ThingsBoard TimescaleDB 调优

  • chunk interval：默认配置 7 天适合中等写入；高写入可缩短，低写入可延长。
  • 压缩：只压历史冷 chunk，设置 segment/order 与查询模式一致，例如按 entity/key 分段、按 ts 排序。
  • retention：尽量用 Timescale retention policy/drop chunk 替代逐行 TTL DELETE。
  • 索引：谨慎增加全局查询索引，每个 chunk 都会有本地索引，写入成本成倍体现。
  • 连续聚合：用于固定粒度看板和长期报表，不替代原始数据查询。

15. 常见踩坑

  • 把 ts_kv 当普通业务表频繁 UPDATE/DELETE，导致 Vacuum 压力。
  • 给遥测表加过多二级索引，写入吞吐下降。
  • 长事务或长时间游标阻塞 Vacuum，old snapshots 保留 dead tuple。
  • 未监控 replication slot，备份/复制停滞撑爆 pg_wal。
  • Timescale chunk 太小导致 chunk 数过多，planner 开销上升；太大导致 retention 和压缩粒度粗。

生产诊断 SQL

-- 当前活动与等待
SELECT pid, usename, state, wait_event_type, wait_event,
       now() - xact_start AS xact_age,
       now() - query_start AS query_age,
       left(query, 300) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_age DESC;

-- 阻塞链
SELECT blocked.pid AS blocked_pid,
       blocker.pid AS blocker_pid,
       blocked.query AS blocked_query,
       blocker.query AS blocker_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocker
  ON blocker.pid = ANY(pg_blocking_pids(blocked.pid));

-- 表膨胀与vacuum状态
SELECT relname, n_live_tup, n_dead_tup,
       last_vacuum, last_autovacuum,
       last_analyze, last_autoanalyze,
       vacuum_count, autovacuum_count
FROM pg_stat_all_tables
WHERE schemaname = 'public'
ORDER BY n_dead_tup DESC
LIMIT 30;

-- XID年龄
SELECT datname, age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;

-- WAL统计
SELECT * FROM pg_stat_wal;

-- checkpoint统计
SELECT checkpoints_timed, checkpoints_req,
       checkpoint_write_time, checkpoint_sync_time,
       buffers_checkpoint, buffers_clean, buffers_backend
FROM pg_stat_bgwriter;
