详细步骤说明

  1. 设备发送数据：设备通过MQTT发布到 topic v1/devices/me/telemetry，payload为JSON格式
  2. Transport层解析：MqttTransportHandler 解析MQTT消息，转换为 PostTelemetryMsg (Protobuf)
  3. 推入消息队列：DefaultTransportService 将消息编码后通过 TbQueueProducer 发送到Kafka
  4. Consumer消费：TbRuleEngineConsumerService 从Kafka拉取消息，反序列化为 QueueToRuleEngineMsg
  5. Actor路由：消息通过 Actor 系统路由到对应租户的 Root Rule Chain
  6. 规则链处理：按配置的节点链式处理，通常包括保存数据、告警检查、外部推送等
  7. 数据持久化：Save Timeseries 节点将数据写入 PostgreSQL/Cassandra

详细步骤说明

  1. 用户发起RPC：通过REST API或规则引擎节点发送RPC请求
  2. 权限验证：RpcController验证用户权限和设备归属
  3. Device Actor处理：查找设备当前的活跃Transport会话
  4. 消息路由：如果设备连接在其他节点，通过Kafka路由到对应Transport
  5. Transport下发：Transport层通过MQTT在对应topic发布RPC消息
  6. 设备接收：设备订阅 rpc/request/+ topic 接收命令
  7. 响应回传：设备响应通过 rpc/response/{id} 回传到平台

详细步骤说明

  1. 遥测数据到达：设备上报的遥测数据进入规则链处理
  2. 配置文件检查：Device Profile Node 根据设备配置文件的告警规则进行条件评估
  3. 告警创建：条件满足时创建告警（含严重程度、类型、详情）
  4. 告警持久化：保存到数据库，包含关联设备、时间戳、状态
  5. 通知分发：通过配置的通知渠道（邮件、短信、Slack等）发送告警
  6. 实时推送：通过WebSocket推送到已订阅的前端界面
  7. 告警传播：告警从设备传播到关联的资产、客户、租户层级

三种属性类型

  1. 客户端属性(Client)：设备主动上报，如固件版本、电池电量。设备可读写，服务端只读
  2. 共享属性(Shared)：服务端设置，推送给设备。如配置参数、开关状态。设备只读，变更时主动推送
  3. 服务端属性(Server)：仅服务端使用，设备不可见。如地理位置、安装日期等管理信息

集群分区机制

  1. 一致性Hash：每个实体(设备)通过 entityId 的 hash 映射到固定的 Kafka 分区
  2. 分区分配：每个 Core 节点负责消费一组分区，保证同一设备的消息总是由同一节点处理
  3. 再平衡：节点加入/退出时，通过 Zookeeper 协调重新分配分区
  4. Transport路由：Transport 层根据目标实体的分区信息，将消息发送到正确的 Kafka 分区
  5. 跨节点RPC：如果设备连接在 Node A，但 Actor 在 Node B，RPC响应通过 Kafka 路由
