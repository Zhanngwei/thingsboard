ThingsBoard 3.6.4 核心数据库表与关系图

本图回答三个问题：核心表保存什么、主要字段是什么、表之间如何关联。实体元数据、告警、规则链等长期保存在 PostgreSQL；遥测后端可配置为 PostgreSQL 分区表、TimescaleDB hypertable 或 Cassandra 宽表。

数据域默认/可选后端主要表职责
租户、用户、设备、资产、规则链、告警PostgreSQLtenant、device、asset、rule_chain、alarm关系型元数据、事务更新、列表检索和权限归属。
属性PostgreSQLattribute_kv保存实体当前属性值及作用域，不保存完整历史曲线。
历史遥测cassandra / sql / timescalets_kv 或 ts_kv_cf按实体、key、时间范围保存和查询历史数据点。
最新遥测cassandra / sql / timescalets_kv_latest 或 ts_kv_latest_cf每个实体每个 key 只保留当前最新值，服务仪表盘和实体查询。
关键点：database.ts.type 和 database.ts_latest.type 是两个开关。历史遥测与最新遥测可以走不同实现；选择 timescale 时，只有历史表 ts_kv 被转为 hypertable，ts_kv_latest 仍是普通 PostgreSQL 表。

2. 关系阅读规则

数据库真实外键 应用层逻辑关联/多态关联

ThingsBoard 为了支持多种实体类型，大量使用 entity_type + entity_id。例如属性、关系、告警传播、遥测都可能指向 Device、Asset、Customer、Tenant 等不同表，因此数据库无法给它们建立单一外键。

不要按传统 ER 图误读：tenant_id、customer_id、originator_id 等很多列在业务上有关联，但 schema 未声明 FK。删除、权限校验和一致性主要由 ThingsBoard Service/DAO 层控制。

device

设备主档案。只保存身份、归属、profile、固件和扩展配置，不把温度/电压等动态值做成列。

device_profile

设备行为模板。定义 transport/provision 类型、profile JSON、默认规则链、队列、仪表盘及固件关联。

device_credentials

设备认证凭证。device_id 唯一，表达设备与凭证的一对一关系。

asset / asset_profile

用于楼宇、产线、机房等业务资产建模；Asset 也可以拥有属性、遥测和告警。

relation

通用实体关系边。用 from/to 的 ID 和类型支持 Device-to-Asset、Asset-to-Asset 等任意拓扑。

entity_view

原实体的受限视图，可限定可见 keys 和时间范围，常用于客户侧数据授权。

alarm 是告警本体；entity_alarm 是实体到告警的查询索引/关联表；alarm_comment 保存评论和系统事件；alarm_types 保存租户已经使用的告警类型集合。

字段组含义
originator_id + originator_type最初产生告警的实体，多态关联 Device、Asset 等。

cleared/clear_ts告警是否已清除以及清除时间。
propagate*是否把告警传播到 owner、tenant 或特定关系类型。

字段作用

8. 遥测统一逻辑模型

flowchart TB
  Entity[Device / Asset / Customer / Tenant / Other Entity]
  Key[temperature / humidity / active]
  Point[Telemetry Point]
  Id[entity_id]
  Time[ts 毫秒时间戳]
  Value[bool / str / long / double / json]
  History[历史遥测]
  Latest[最新遥测]

  Entity --> Id --> Point
  Key --> Point
  Time --> Point
  Value --> Point
  Point --> History
  Point --> Latest

无论使用哪种后端，业务对象都是 TsKvEntry：实体、key、时间戳、一个类型化值。区别只在物理表和分区方式。

逻辑概念PostgreSQL/TimescaleDBCassandra
实体类型历史/最新表不存 entity_type，依赖全局 UUID 和业务上下文显式存 entity_type，参与 partition key
keyts_kv_dictionary 把字符串映射为 int直接保存 text key
历史点ts_kvts_kv_cf
最新点ts_kv_latestts_kv_latest_cf
类型化值bool_v、str_v、long_v、dbl_v、json_v 中仅一个有值

表主键功能
ts_kv(entity_id, key, ts)历史遥测父表，按 ts 做 PostgreSQL RANGE 分区；默认分区粒度配置为 MONTHS。
ts_kv_latest(entity_id, key)保存每个实体每个 key 的最新值，避免从历史表排序取最后一条。
ts_kv_dictionarykey，另有唯一 key_id把重复的遥测字符串 key 压缩成整数，减少历史表和索引体积。

10. TimescaleDB 遥测表

flowchart TB
  App[ThingsBoard TimescaleTimeseriesDao]
  Logical[ts_kv logical hypertable]
  Router[Timescale chunk router by ts]
  C1[_hyper chunk A]
  C2[_hyper chunk B]
  C3[_hyper current chunk]
  Index1[(entity_id,key,ts index)]
  Index2[(entity_id,key,ts index)]
  Index3[(entity_id,key,ts index)]
  Latest[ts_kv_latest<br/>ordinary PostgreSQL table]

  App --> Logical --> Router
  Router --> C1 --> Index1
  Router --> C2 --> Index2
  Router --> C3 --> Index3
  App --> Latest
  App --> Dict

TimescaleDB schema 先创建普通 ts_kv，安装服务再执行：

SELECT create_hypertable(
  'ts_kv',
  'ts',
  chunk_time_interval => 604800000,
  if_not_exists => true
);
对象主要字段/键功能
ts_kv hypertable仍为 (entity_id, key, ts)应用看到的逻辑大表；写入和查询 SQL 与 PostgreSQL 版本基本一致。
chunk按 ts 的时间区间TimescaleDB 自动创建的物理子表，负责写入路由和时间范围裁剪。
ts_kv_latest(entity_id, key)仍是普通 PostgreSQL 表，不是 hypertable。
ts_kv_dictionarykey / key_id与 SQL 后端相同的 key 字典。
3.6.4 默认 Timescale chunk interval 配置为 604800000 ms，即 7 天。真实生产应按每日写入量、索引大小和查询窗口重新评估。

11. Cassandra 遥测表

flowchart TB
  Entry[Telemetry entry]
  PartitionCalc[按时间计算 partition bucket]
  Registry[ts_kv_partitions_cf<br/>记录存在的bucket]
  History[ts_kv_cf]
  PKey[Partition Key<br/>entity_type, entity_id, key, partition]
  Cluster[Clustering key ts]
  Latest[ts_kv_latest_cf]
  LatestKey[Partition Key<br/>entity_type, entity_id]
  LatestCluster[Clustering key key]

  Entry --> PartitionCalc
  PartitionCalc --> Registry
  PartitionCalc --> History --> PKey --> Cluster
  Entry --> Latest --> LatestKey --> LatestCluster
表Primary Key主要功能
ts_kv_cf((entity_type, entity_id, key, partition), ts)历史遥测。先按实体、key、时间桶定位分区，再按 ts 聚簇排序。
ts_kv_partitions_cf((entity_type, entity_id, key), partition)登记某实体/key 已存在的时间分区，帮助跨时间范围查询找到要扫的分区。
ts_kv_latest_cf((entity_type, entity_id), key)同一实体的各个最新 key 聚集在一个 Cassandra partition 中。
Cassandra 没有关系型 JOIN：实体、key、时间分区信息必须完整地编码进主键。表结构不是从 ER 关系推导出来的，而是从查询模式反向设计。
