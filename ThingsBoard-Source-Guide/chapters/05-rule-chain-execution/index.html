Rule Chain 执行流程

ThingsBoard 3.6.40cb411fc90Queue Pack CallbackChain/Node ActorPostgreSQL Graph

本章从 ToRuleEngineMsg 被 consumer poll 开始，跟踪 App/Tenant/RuleChain/RuleNode Actor、关系路由、嵌套链、跨分区和 fan-out，直到 Processing Strategy commit 或 reprocess；同时解释 Rule Chain 图的保存与热更新。

核心结论：本地单目标路由共用原 callback；跨分区或多目标路由会创建新的 Queue 消息，父消息只等待 producer handoff。默认 Main Queue 使用 SKIP_ALL_FAILURES，失败或超时不自动触发 broker retry。Queue offset、Rule Node 数据库事务和外部副作用没有共同事务。

一、流程目标

Rule Chain 是可热更新的有向处理图。RuleChainActor 管理 first node 和 relations，RuleNodeActor 管理一个 TbNode 运行实例，Rule Engine Queue 管理服务隔离、分区、pack timeout 和提交策略。

数据面Rule Engine QueueQueue record、Actor 内存图、业务后端由 callback 和 Processing Strategy 决定，不是全链路事务

Relation 终态

  • 无匹配 Failure relation：callback failure。
  • 无匹配 Success/custom relation：callback success。
  • 单目标且本地：继续共用原 callback。
  • 跨分区或多目标：复制新 UUID 并重新入 Queue。

嵌套 Rule Chain

标准 metadata 保存把 nested connection 转成合成 TbRuleChainInputNode。它把 caller chain/node 压入 TbMsgProcessingCtx stack；目标 TbRuleChainOutputNode 以节点名称作为 label，pop stack 后从 caller input node 按 label 继续。

sequenceDiagram
  participant C as Caller Node
  participant I as TbRuleChainInputNode
  participant T as Target Chain
  participant O as TbRuleChainOutputNode
  participant R as Caller Chain
  C->>I: relation message
  I->>I: push caller chain/node to stack
  I->>T: RuleChainInputMsg
  T->>O: execute target graph
  O->>O: pop stack, output label = node name
  O->>R: RuleChainOutputMsg
  R->>R: route from caller input node by label

运行时兼容 target 直接为 RULE_CHAIN 的 relation，但该路径不压 caller stack，因此不会建立 output 返回点。标准 UI 保存使用合成 Input Node 模型。

TbMsg 执行字段

id 是当前 record callback key；ruleChainId/ruleNodeId 控制目标和 resume；ctx 保存节点计数和 nested stack；callback 是 transient，Queue consumer 反序列化时注入新的 callback。详见 toByteArray 和 fromBytes。

MultipleTbQueueTbMsgCallbackWrapper 聚合的是 producer 入队结果，不是子 Rule Chain 完成结果。完整类清单、接口和 callback wrapper 分析见 Markdown 版。

Node 删除会先走 processor onStop，Actor 销毁时又调用 stop；当前实现不清空 tbNode，自定义 TbNode.destroy() 应可重复执行。

Singleton Node

普通 Node 在当前 Rule Chain 服务执行；singleton Node 按 RuleNodeId 分区。非 owner 创建新 UUID 消息、以空 callback 重新入 Queue，再立即 ack(source)。它提供单实例位置约束，不提供事务性交接。

Actor 适合把可变图和 Node 生命周期绑定到 mailbox，但它串行化的是调用入口，不是异步业务完成。详细创建/停止/分区流程见 Markdown 版。

九、Kafka 分析

项目Main Queue 默认源码语义
Name / TopicMain / tb_rule_engine.maintopic 还可能被部署前缀改写
Logical partitions10Kafka 下通常形成 tb_rule_engine.main.0 到 .9 的独立物理 topics
Client IDre-Main-consumer-{serviceId}-{counter}每个 consumer 唯一
Groupre-Main-consumerisolated tenant 包含 tenantId
Pack timeout2000 ms不是单 Node timeout
SubmitBURSTpoll pack 全部提交 Actor
ProcessingSKIP_ALL_FAILURES失败/超时直接 commit

这些不是单个 Kafka topic 内的 10 个原生 partitions。3.6.4 每个物理 topic 的原生 partition 默认是 1，consumer 使用 subscribe(topicNames)。平台安装默认 Queue provider 是 in-memory；只有启用 Kafka 时 group 和 commitSync() 才成立。

Submit Strategy

BURST 全部提交；BATCH 分批；SEQUENTIAL 一条 success 后下一条；SEQUENTIAL_BY_ORIGINATOR 和 SEQUENTIAL_BY_TENANT 只在各自 key 内串行。BATCH/SEQUENTIAL 的 failure 会阻断后续提交直到 timeout，而 pending map 从一开始就包含尚未提交的尾部消息；顺序范围仅限当前 consumer poll pack。

Processing Strategy

策略重处理集合关键风险
SKIP_ALL_FAILURES无commit 后 late callback 仍 valid
SKIP_ALL_FAILURES_AND_TIMED_OUT无只阻止后续检查点，不能撤销已发副作用
RETRY_FAILED/TIMED_OUT选定 failed/pending旧 attempt 部分副作用可能已完成
RETRY_ALLfailed/pending/success明确重复成功副作用

Retry Strategy 先复制 reprocess map，可能 sleep，manager 随后才 cleanup；窗口内完成的旧 callback 不会从已复制 map 中移除。maxRetries=3 表示原始 attempt 后最多再处理 3 次。

  • Rule Chain/Node configuration 在 DDL 中是 varchar，由 JPA JsonStringType 映射 JsonNode，不是 JSONB。
  • rule_node.rule_chain_id、first_rule_node_id 和多态 relation 没有实体 FK，完整性主要由 Java validator 和显式 cleanup 保证。
  • Metadata 的 Node/Relation/first-node 修改处于 BaseRuleChainService.saveRuleChainMetaData(...) 单个 PostgreSQL transaction。
  • VC、lifecycle notification、related-chain update 和 audit 在 transaction 返回后执行。
  • Relation from/to 查询有事务缓存；关系保存/删除事件在 transaction 完成后 evict 精确 cache keys，provider 可为 Caffeine 或 Redis。
  • validateRuleNode(...) 捕获插件反射/配置解析异常后返回错误字符串，但 metadata 保存调用点未检查返回值；不能保证所有无效 Node 配置都阻止提交。
  • 运行时业务 Node 使用各自 DAO transaction；不存在包住整条 Rule Chain 的 Spring transaction。

DDL 证据：rule_chain、rule_node、relation。

关键生产措施：为外部副作用设计业务幂等键；关键链使用专用 Queue；同时监控 pack timeout、Node failure、notification lag 和下游延迟；不要把 RETRY_ALL 当成无成本可靠性开关。

十三、常见面试题

tellSuccess 是否表示整链成功？

不是。它选择 Success relation；无匹配后继才完成 callback。

Rule Node 异常后 Kafka 一定重试吗？

不一定。异常先走 Failure relation；无后继才 callback failure，而默认 Main Queue 会 skip failure 并 commit。

多分支是否等待全部分支业务完成？

不等待。父 callback 只聚合多个子消息的 producer 入队结果，子记录以后独立消费。

Actor 是否保证设备消息全局顺序？

不保证。单 mailbox 只串行同步入口；不同 NodeActor、异步 Future、partition 和重新入 Queue 都可并发。

Metadata 保存是一个事务吗？

Nodes、relations 和 first node 是一个 PostgreSQL transaction；通知、VC、related chains 和 audit 在其后。

Rule Node configuration 是 JSONB 吗？

不是。3.6.4 DDL 是 varchar，JPA 映射为 JsonNode。

嵌套链如何返回？

Input Node 压 caller stack，Output Node 用名称作为 label，pop 后回 caller input node 继续路由。

默认 timeout 会取消 Node 吗？

不会。SKIP_ALL_FAILURES cleanup 后 callback 仍 valid；已发出的 DAO/HTTP 操作也无法撤销。

Singleton Node 是否 exactly-once？

不是。它约束执行 owner，但源消息在重新入 Queue 后立即 ack，且不等待 producer callback。

如何提升关键链可靠性？

专用 Queue、明确 retry 范围、业务幂等、唯一约束/upsert、外部 request id、补偿路径和 notification 收敛监控需要同时设计。

其余面试题及标准答案见 Markdown 版。
