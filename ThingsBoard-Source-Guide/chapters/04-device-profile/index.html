Device Profile 流程

ThingsBoard 3.6.40cb411fc90PostgreSQL JSONBTransport Hot UpdateNon-atomic Default Switch

本章覆盖 Device Profile 创建、更新、重命名、默认切换和删除，并追踪 Transport、Rule Engine、Alarm Rules、Provision、OTA、Edge 与三套 Profile cache。

核心结论：标准 Profile 保存没有应用层外事务。Profile 行先在 DAO 事务中提交，随后才逐台同步 device.type、广播 Cluster、扇出 OTA 并发送 entity action。默认切换由两个独立 DAO 事务完成，数据库也没有“每租户一个默认”的唯一约束。

一、流程目标

Device Profile 是设备群组的运行策略，而不是单纯分类。它决定协议解析、Provision、默认 Rule Chain/Queue、Alarm Rules、默认 Dashboard 与 OTA 继承。

配置区域影响主要消费者
transport_type + transportConfigurationtopic、payload、Protobuf、LwM2M/SNMP 参数Transport cache 与 active Session
provision_type + provisionConfiguration自动创建设备、预注册、X.509DeviceProvisionService / Transport API
default_rule_chain_id / default_queue_name消息入队前改写路由DefaultTbClusterService
profile_data.alarms按 DeviceState 判断创建/清除告警TbDeviceProfileNode
firmware_id / software_id未覆盖 OTA 的 Device 继承DefaultOtaPackageStateService

3.2 默认切换

flowchart TD
  R[set default] --> O[save old default false Tx 1]

  E --> A[old and target ENTITY_UPDATED plus audit]
  O -->|target save fails| Z[tenant may have no default]

DeviceProfileServiceImpl.setDefaultDeviceProfile(...) 没有外层事务；DDL 也没有 partial unique index。默认切换不调用 Transport Profile 广播或 lifecycle，只发送旧/新 Profile 的 entity action 与审计。

八、Actor 分析

没有 Device Profile Actor。Lifecycle consumer 会把消息发送到 AppActor -> TenantActor，但继承的 entity actor resolver 只解析 RULE_CHAIN，Profile 找不到目标。Rule Node 的 Profile/Alarm 状态由 cache listener 给自己发送 self message 后串行更新。

sequenceDiagram
  participant Q as Lifecycle Queue
  participant C as Consumer
  participant K as Profile cache
  participant N as TbDeviceProfileNode
  participant A as AppActor TenantActor
  Q->>C: Profile UPDATED
  C->>K: evict and reload
  K->>N: listener fresh Profile
  N->>N: self DEVICE_PROFILE_UPDATE_SELF_MSG
  C->>A: high priority lifecycle
  A-->>A: no Profile Actor target

九、Kafka 分析

Kafka 是可选 Queue 实现，默认可使用 in-memory。启用 Kafka 后，Transport notification、Core lifecycle、Rule Engine lifecycle、Rule Engine data 和 OTA state 是独立逻辑通道。

通道消息路由
Transport notification完整 Profile update / ID delete每个 Transport serviceId 一份
Core/RE lifecycleComponentLifecycleMsg每个 Core/Rule Engine serviceId
Rule Engine dataENTITY_CREATED/UPDATED/DELETEDqueueName + tenantId + profileId
OTA state每 Device ToOtaPackageStateServiceMsgOTA producer 默认 topic
顺序边界：这些通道没有跨 topic 全序，也没有 transactional outbox。多数调用传 callback=null，HTTP 不等待消费者完成。

erDiagram
  DEVICE_PROFILE ||--o{ DEVICE : "FK restrict"
  DEVICE_PROFILE ||--o{ OTA_PACKAGE : "FK cascade"
  RULE_CHAIN ||--o{ DEVICE_PROFILE : defaults
  DASHBOARD ||--o{ DEVICE_PROFILE : default
  OTA_PACKAGE ||--o{ DEVICE_PROFILE : firmware_software
  DEVICE_PROFILE {
    uuid id PK
    uuid tenant_id
    varchar name
    varchar transport_type
    varchar provision_type
    jsonb profile_data
    boolean is_default
    uuid default_rule_chain_id
    varchar default_queue_name
  }
  DEVICE {
    uuid id PK
    uuid device_profile_id FK
    varchar type
  }

PostgreSQL 保证 tenant/name、tenant/externalId、全局 provision key 唯一，并维护 Rule Chain、Dashboard、OTA、Device FK。没有 default partial unique index。Profile 本身不写 TimescaleDB/Cassandra；只有 OTA 扇出产生的 Device telemetry 才按部署选择时序后端。

三套 cache 必须分开排障：DAO Caffeine/Redis、Rule Engine 进程内 Profile cache、Transport 进程内 Profile cache/Session。一次 Redis DEL 不代表运行时全部刷新。

十一、异常处理

失败点数据库结果运行时风险
校验失败Profile 未写无 Cluster 消息
Profile SQL 失败Profile 回滚，image 可能已提交可能留下未引用 image
重命名第 N 台 Device 失败Profile 和前 N-1 台已提交Cluster Profile update 尚未发送
Transport/lifecycle producer 失败Profile 已提交节点 cache/Session 分裂
默认切换第二次 save 失败旧默认已 false租户没有默认 Profile
并发默认切换可能多个默认请求各自产生 action/audit
删除遇到 Device FK删除事务整体回滚Cluster delete 尚未发送
删除 commit 后通知失败Profile 已删除Transport/RE/Edge 可保留旧 cache

生产巡检应检查每个 tenant 的 default 数量、Profile 与 device.type 一致性、notification lag、活跃 Session 解析行为和 OTA 扇出进度。HTTP error 不足以判断 Profile 是否已提交。

十二、源码阅读路线

  1. DeviceProfile、DeviceProfileData 和 schema-entities.sql：先建立字段/FK/JSONB 模型。
  2. DeviceProfileController、DefaultTbDeviceProfileService：标记三条写入口和应用副作用顺序。
  3. DeviceProfileServiceImpl.doSaveDeviceProfile：确认 Profile commit 与 rename loop 的先后。
  4. DeviceProfileDataValidator：把配置字段映射到 Queue、Transport、Alarm、Rule Chain、Dashboard 与 OTA。
  5. setDefaultDeviceProfile 与 DDL：审查两个事务、默认唯一约束缺口和 provision cache key。
  6. deleteDeviceProfile：确认 default 保护、Device FK、cascade 和 after-commit event。
  7. DefaultTbClusterService、DefaultTransportService、DeviceSessionCtx：追踪协议热更新。
  8. AbstractConsumerService、DefaultTbDeviceProfileCache、TbDeviceProfileNode：追踪 Alarm Rules 热更新。
  9. DefaultOtaPackageStateService：理解小配置更新如何扇出为大量 Device 时序写。

十三、常见面试题

Profile 保存是一个事务吗？

Profile 行本身是一个 DAO 事务；Image、Device rename、Cluster、OTA、Rule Engine 与 Audit 不在同一个事务。

为什么重命名可能部分成功？

Profile 先 commit，关联 Device 每台各自 commit，失败无法回滚前序结果。

数据库保证一个租户一个默认 Profile 吗？

不保证；应用检查和两个独立 save 无法覆盖并发或中途失败。

在线 MQTT Session 如何使用新 Profile？

Transport 收到完整 Profile 后按 ProfileId 扫描 Session，重建 topic filters、payload/Protobuf descriptors 和 adaptor，无需正常重连。

Profile 有 Actor 吗？

没有。Actor lifecycle 找不到 Profile target；Rule Node 通过 cache listener + self message 更新 Alarm Rule 状态。

Profile 如何决定 Rule Engine 路由？

producer 前读取 Profile，使用 defaultRuleChainId/defaultQueueName 改写 TbMsg，再解析 partition。

删除 Profile 会删除 Device 吗？

不会；Device FK 会阻止删除，且 default Profile 由服务直接拒绝。

Profile 为什么使用 JSONB？

协议、Provision 和 Alarm Rule 是多态且演进快；常用约束字段仍拆列，深层结构由 Jackson 和 validator 管理。

Kafka 是否让 Profile 与数据库一致？

不会。无 outbox、跨 topic 无全序、consumer 异步，Kafka 只实现 Queue SPI 的一种部署。
