Device 删除流程

ThingsBoard 3.6.40cb411fc90REST → PostgreSQLPre-commit QueueTelemetry retained

本章追踪 DELETE /api/device/{deviceId} 从权限检查、Alarm/Device 聚合删除，到 Transport、Device State、Actor、Rule Engine 和审计的完整链路，并把直接 DAO 删除与 Edge 解除绑定作为不同入口处理。

核心结论：标准 REST 删除的 Alarm、Credentials、Relations、entity-alarm 与 Device 处在同一外层事务中；Gateway、Transport、Core、lifecycle 和 ENTITY_DELETED 在该事务提交前发送。attribute_kv、ts_kv、ts_kv_latest、Cassandra telemetry 和设备 RPC 不会自动清理。

一、流程目标

删除流程既要撤销 Device 的持久身份，也要让分布式运行时停止接受该 Device 的连接和消息。这两部分使用不同的一致性机制：前者依赖 PostgreSQL 本地事务，后者依赖 Queue、Actor 和协议回调。

八、Actor 分析

数据库删除不经过 Actor。Lifecycle consumer 到达 TenantActor.onComponentLifecycleMsg(...) 后，删除分支调用 getOrCreateDeviceActor(...)，高优先级投递 DeviceDeleteMsg，随后把 ID 放入 deletedDevices。DeviceActor 对该消息唯一动作是 ctx.stop(ctx.getSelf())。

sequenceDiagram
  participant Q as Lifecycle Queue
  participant C as Notification Consumer
  participant T as TenantActor
  participant D as DeviceActor
  Q->>C: Device DELETED
  C->>C: evict Device to Profile cache
  C->>T: lifecycle high priority
  T->>D: getOrCreate + DeviceDeleteMsg
  T->>T: deletedDevices.add
  D->>D: ctx.stop(self)

若 Actor 原先不存在，删除可能短暂创建它再停止。Consumer 在 commit 前运行时可能读到旧 Device；commit 后运行时初始化查询返回 null，但高优先级删除消息仍能触发停止。

九、Kafka 分析

Kafka 不是必需路径。默认 queue.type=in-memory；设置 TB_QUEUE_TYPE=kafka 后，同一 Queue SPI 才使用 Kafka producer/consumer。

逻辑 Queue路由Consumer
Transport notification每个 TB_TRANSPORT serviceId 的 notification topicTransport consumer
Core statetenantId + deviceId 的 Core partitionDefaultTbCoreConsumerService
Lifecycle notification每个 TB_RULE_ENGINE serviceIdDefaultTbRuleEngineConsumerService
Rule Engine dataqueueName + tenantId + entityIdTbRuleEngineQueueConsumerManager
顺序边界：四类消息位于不同 topic/producer，没有跨 topic 全序；callback 基本为 null，也没有 transactional outbox。Rule Node 不能假设 Session 已关闭或 Actor 已停止。

十、数据库分析

PostgreSQL

device_credentials.device_id 只有 UNIQUE，没有 Device FK；relation、attribute_kv、alarm.originator_id、entity_alarm.entity_id 都是多态引用。只有 alarm_comment.alarm_id 和 entity_alarm.alarm_id 对 Alarm 声明级联。

TimescaleDB

本链不删除 hypertable ts_kv，也不删除普通 latest 表 ts_kv_latest。3.6.4 的 SQL/Timescale TTL 过程通过当前 device 表按 tenant/customer 反查 EntityId；Device 行删除后，orphan history 可能无法再由该路径命中。

Cassandra

删除 PostgreSQL Device 不调用 Cassandra DAO。History 只可能按写入 TTL 自行过期；latest 或无 TTL 数据需要独立清理。

Redis/Caffeine

事务内只发布缓存事件；默认 @TransactionalEventListener 在成功提交后清本地或 Redis key。跨服务运行时缓存通过 Cluster notification 传播。

十一、异常处理

失败点DB 结果分布式副作用
Entity View 存在整个外层事务回滚，Alarm 恢复Device 通知尚未发送
SQL/约束错误回滚发生在通知前时无 Device runtime 消息
前一个 Queue send 成功，后一个同步失败回滚已发送消息不会撤销，Session/State/Actor 可能误删
producer 异步失败仍可 commit部分节点收不到删除；HTTP 仍可能 200
ENTITY_DELETED push 失败内部 catch，仍可 commitRule Chain 不感知删除
Audit executor 失败Device 事务不受影响审计缺失
客户端超时后重试可能已 commit重试会因 Device not found 失败

JpaRelationDao 和 BaseRelationService 捕获部分 ConcurrencyFailureException 只写 debug。PostgreSQL 事务可能已 abort，或关系未可靠清完；必须检查最终 commit 与 orphan relation，不能把 catch 后继续执行当成成功。

大告警量风险：TimePageLink(Integer.MAX_VALUE) 一次加载全部 AlarmId，再逐条删除。高告警量设备会放大 JVM 内存、事务时长、锁、WAL 和 dead tuples。

十二、源码阅读路线

  1. DeviceController.deleteDevice(...)：权限和删除前 Device 快照。
  2. DefaultTbDeviceService.delete(...)：先标出外层事务。
  3. AbstractTbEntityService.removeAlarmsByOriginatorId(...)、BaseAlarmService.delAlarm(...)：Alarm 聚合。
  4. DeviceServiceImpl.deleteDevice(...)：引用检查和实际删除顺序。
  5. DeviceCredentialsServiceImpl、BaseRelationService、JpaRelationDao：无 FK 聚合清理。
  6. DefaultTbNotificationEntityService.notifyDeleteDevice(...)：确认通知在 commit 前。
  7. DefaultTbClusterService.onDeviceDeleted(...)、EntityActionService：四类 Queue。
  8. DefaultTransportService 与协议 listener：Session 清理。
  9. DefaultDeviceStateService、TenantActor、DeviceActor：State 与 Actor 生命周期。
  10. schema-entities.sql、schema-timescale.sql、schema-ts.cql：用物理模型验证残留数据。

十三、常见面试题

标准删除的事务边界在哪里？

DefaultTbDeviceService.delete(Device, User) 的 @Transactional，Alarm 与 Device 聚合删除加入同一事务。

Cluster 通知在 commit 后吗？

不是。Gateway、Transport、Core、lifecycle 和 ENTITY_DELETED 都在 commit 前；transaction listener 的缓存与 Edge 事件才是 AFTER_COMMIT。

为什么不能只用 ON DELETE CASCADE？

关系、属性、告警传播和遥测是多态引用，且 Session、Actor、Rule Engine 不是数据库对象。

删除会清 TimescaleDB/Cassandra 吗？

不会。两种后端都没有进入调用链；SQL/Timescale orphan history 甚至可能无法再被基于当前 Device 表的 TTL 过程命中。

删除会预建 Device Actor 吗？

可能。TenantActor 的删除分支调用 getOrCreate，再用 DeviceDeleteMsg 立即停止；创建 lifecycle 则不会这样做。

Queue send 成功是否代表 DB 已删除？

不代表。send 发生在 commit 前，DB 后续仍可回滚。

Kafka 是必需的吗？

不是。默认 Queue 实现是 in-memory，Kafka 只是可选物理实现。

如何实现严格删除一致性？

数据库 outbox、幂等消费者、删除 tombstone、可重试的跨后端清理任务和明确补偿，不能依赖当前 pre-commit fire-and-forget 消息。
