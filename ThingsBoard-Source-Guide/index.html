31 Timeseries TTL 清理流程

SYS partition owner 调度、PostgreSQL 分区与行清理、Timescale DELETE、Cassandra cell TTL、latest 分叉和存储回收风险。

已完成 · Markdown · PlantUML · 时序图 SVG · 架构图 SVG

源码结论：3.6.4 中普通 MQTT 遥测不会先进入 Device Actor。Transport 直接投递 Rule Engine Queue，消费者再进入 App/Tenant/RuleChain/RuleNode Actor。MQTT PUBACK 表示队列 producer 写入成功，不表示数据库落库完成。
Device 创建结论：device 与 device_credentials 在一个 PostgreSQL 事务中提交；Cluster、Rule Engine、State 和 Audit 是提交后的异步传播。DEVICE CREATED 生命周期不会预建 Device Actor。
Device 删除结论：Alarm 与 Device 聚合删除共享外层 PostgreSQL 事务，但运行时 Queue 在 COMMIT 前发送。删除不清理 Attribute、TimescaleDB/Cassandra telemetry 或设备 RPC；DEVICE DELETED 可能临时创建 Device Actor 再停止。
Device Profile 结论：Profile 行先于重命名、Cluster、OTA、Rule Engine 与 Audit 提交；默认切换由两个独立 DAO 事务完成，数据库没有每租户唯一默认约束。Transport 和 Rule Engine 分别通过通知队列热更新 Session 与 Alarm Rule 状态。
Rule Chain 结论：本地单目标沿用原 callback，跨分区或多目标在 producer handoff 后切成独立 Queue records。Main Queue 默认跳过 failure/timeout 并提交；metadata 的 PostgreSQL 图事务与 lifecycle/Actor reload 不原子。
Alarm 创建结论：createAlarm 是按 originator + type 的 active upsert；已有行加锁，但首次并发创建没有唯一约束。alarm、entity_alarm、WebSocket、通知、Rule Engine action 与 audit 不共享事务。
Alarm 清除结论：clear_alarm 通过行锁保证首次更新和重复 no-op，但数据库、WS、通知、comment、Rule Engine、audit 与 Edge 不原子。REST、显式 Node、Device Profile 和 Edge 上行产生的消息及回调并不相同。
Attributes 结论：attribute_kv 只保存最新状态；多 key 请求无统一事务。启用缓存后，DB 已提交仍可能因 cache transform 失败而抑制通知；跨节点 update proto 还会丢失 notifyDevice=false。
Telemetry 结论：history 与 latest 可独立选择后端并独立提交。SQL/Timescale 请求 TTL 不驱动删除，后台按 system/tenant/customer TTL 清 history 且不清 latest；3.6 也未自动配置 continuous aggregate、compression 或 retention policy。
RPC 结论：REST 先经规则链再到 Device Actor；只有到达 Actor 时未过期的 persistent RPC 才保存 QUEUED 并回调 rpcId。DB 状态、状态 Queue message、MQTT delivery、设备业务 response 和 Node continuation 是不同阶段。
OTA 结论：Device override 优先于 Profile；Queue 与 QUEUED Telemetry 独立。consumer 只调度 INITIATED Future 即返回，commit 可能早于 Shared Attributes callback，异步失败不受 consumer catch 覆盖。binary 下载绕过 Device Actor，经 Transport API 与共享 cache；PostgreSQL OID 在业务路径仍完整 materialize，分离部署应使用 Redis。
Dashboard 结论：dashboard.configuration 只保存 Widget 查询定义；实体/latest/history/alarm 在运行时通过 EntityData/WebSocket 读取。Customer assignment 双写 relation 与 assigned_customers 且无统一外层事务；列表和直接读取权限分别依赖两侧。Widget 使用同一 cmdId 的两阶段命令，实时点由 Core partition owner 路由到持有 WebSocket 的 service。
Login 结论：/api/auth/login 由 Security Filter 而非 Controller 处理。登录读取全局唯一 email、凭据、密码/锁定策略和 2FA；成功同步更新用户 JSON、异步写 audit，再签发不落库的 JWT。失败计数无原子更新，凭据替换是 delete + insert 两事务；多 Core 节点必须用 Redis 共享 user/session token 失效时间。
JWT 结论：Access Provider不重读用户表，只验证签名、exp和失效 cache；角色与实体权限由 Method Security和 PermissionChecker继续判断。Refresh会重读用户/凭据但不检查密码年龄，旧 refresh仍可复用。WebSocket只在连接认证时验证一次。签名 key异步传播无双 key窗口，且 invalidation TTL取 YAML而实际 refresh寿命可取 DB，生产必须校准并使用共享 Redis。
Actor 结论：3.6 使用自研 JVM 内 Actor；每个 Mailbox以 high/normal 无界队列和 busy CAS保证对象级串行，Actor共享命名 Dispatcher且不绑定固定线程。tell只表示本地入队，普通异常resume不重放，高优先级可饿死normal。分区迁移不复制 Mailbox或session，新owner重新构造状态。
Kafka Producer 结论：ThingsBoard逻辑partition被编码进物理topic后缀，ProducerRecord partition为null；key是UUID字符串，value是Protobuf bytes。首次发送同步ensure topic，broker ack后才回调，但不等待consumer/Actor/数据库。同步失败callback后rethrow，null callback的异步失败只写日志；默认acks=all仍搭配单副本。
Kafka Consumer 结论：poll先推进本地position，Rule Engine再等待整个pack并选择内存重投或commitSync；retry不seek Kafka，也不回滚已经完成的副作用。Main Queue默认跳过failure/timeout。长await可能触发rebalance并与旧异步工作重叠；decode异常没有seek或公共DLQ，后续commit可能越过坏record。
Queue 管理结论：Queue是PostgreSQL配置、多个物理topic、PartitionService和consumer manager的组合。保存、topic创建、null-callback通知与运行时应用不原子；删除也先删行再异步drain/topic delete。逻辑partition进入topic后缀，缩容不回收旧topic；consumerPerPartition切换会重建task。queue表无tenant+name/topic唯一约束。
Cluster 通信结论：ZooKeeper用ephemeral ServiceInfo发现节点，PartitionService按serviceId排序后取模分配owner，并不使用现存但无调用者的ConsistentHashCircle。跨节点Actor消息走broker再进入远端本地Actor；producer callback不等远端应用。拓扑变化分别更新consumer和Actor，mailbox、Session与旧异步工作不迁移。
Cassandra 写入结论：registry、history、latest 是三个独立 Future，没有跨表事务。history 按 entity/type/key/time partition 分桶并使用原生 TTL，latest 不过期且普通 INSERT 没有时间戳保护，旧点后到可以覆盖新值。默认读写一致性级别为 ONE。
TimescaleDB 写入结论：只有 ts_kv 是按 bigint ts 的一维hypertable；history与普通PostgreSQL latest分别合批和提交。3.6未创建Continuous Aggregate、压缩或Timescale retention policy，请求TTL也不写入行；后台procedure按租户策略DELETE history并留下latest。
PostgreSQL 写入结论：实体CRUD、JDBC batch和PL/pgSQL是三条不同路径；事务要从真实Service代理入口判断，异步queue已经切换事务。SQL telemetry动态创建RANGE分区并保留DEFAULT；每实例Hikari默认16连接由Web、JPA和多组writer共享，积压、WAL、锁、dead tuple和autovacuum必须联合排查。
HTTP 设备 API 结论：URL access token每次经Transport API交给Core验证，不走用户JWT。Telemetry/Attribute POST的200只等Rule Engine Queue producer；GET Attributes和HTTP RPC使用临时SYNC session、Core Queue和Device Actor。timeout或断连不取消下游工作，URL token必须在网关和日志中脱敏。
CoAP 结论：Californium处理UDP/DTLS与Observe；plain token逐请求交给Core，X.509 identity按peer缓存于Transport内存。Telemetry/Attributes的2.01只确认Queue producer；SYNC/ASYNC session、Observe、CON RPC ACK和PSM/eDRX状态不与数据库事务绑定，重启后设备需重订阅。
LwM2M 结论：Leshan的Bootstrap与Main Server独立于原生CoAP API。Registration成功早于ThingsBoard session、Read/Observe和数据库；Observe值必须经过Profile映射才进入Rule Engine，默认registration/client状态位于当前进程。
MQTT Gateway 结论：物理设备认证后，每个虚拟设备使用独立DeviceId和sessionId；首条业务消息可隐式连接。批量上报无跨设备原子性，下行依赖nodeId与virtual sessionId，QoS 1物理PUBACK不会自动形成虚拟设备DELIVERED。
Device Provision 结论：三协议统一进入Provision service且不经过Device Actor。device与credentials同事务，provisionState、Cluster、Rule Engine和Audit不原子；create策略对响应丢失没有幂等重试保障。
Device Claim 结论：设备ACK早于Actor写ClaimData，默认Caffeine缓存不跨Core。customer_id更新与Claim数据清理分段提交；并发Customer Claim没有行锁或CAS，Reclaim也存在归属已清空但属性保存失败的窗口。
Session 与 Device State 结论：Transport listener、Actor session和Device State是三套状态；register/deregister不会自动发送OPEN/CLOSED。connect/disconnect与active/inactive是独立轴，状态默认写SERVER_SCOPE attributes，切到telemetry必须同步切换device_info_view。
Telemetry 查询结论：REST 直接经AccessValidator和TimeseriesService读数据库，不走Actor/Kafka；keys读取latest，raw的limit按key且没有cursor。PostgreSQL按bucket发SQL，Timescale运行时time_bucket，Cassandra跨partition合并；亚秒interval可绕过700区间真实限制，SQL未知key查询还可能写dictionary。
Timeseries TTL 结论：调度只进入history DAO，不清latest。普通PostgreSQL先DROP完整旧分区再按tenant/customer TTL删除行；Timescale 3.6只做DELETE；Cassandra在写入时绑定cell TTL。SQL request TTL不存入行，procedure还存在TTL cutoff变量跨loop残留风险。
